# Лаба 3 — Собери платформу для shop

В этой лабораторной собрала платформу для небольшого магазина: API, worker и PostgreSQL. Настроила политики допуска, проверила восстановление подов, rolling update и rollback, а потом специально отключила API-сервер и посмотрела, что продолжит работать 🙂

Использовала ту же Ubuntu Server ARM64 в UTM на Mac с Apple Silicon и кластер Minikube `lab2` из второй лабы. Название профиля оставила прежним: в нем уже работает мониторинг. Приложение разместила в namespace `lab3`.

## Часть 0 — Сервисы и подготовка стенда

Перед началом проверила время, память, место на диске и состояние кластера. На VM доступно около 11 ГиБ RAM, на корневой файловой системе оставалось 28 ГБ. Нода была `Ready`, все компоненты мониторинга работали.

Новый стек мониторинга не устанавливала — дальше использовала Prometheus, Grafana, Alertmanager и Karma из второй лабораторной.

Для приложения подготовлены два сервиса:

| Сервис | Что делает |
|---|---|
| `api` | Принимает заказы и возвращает их список из PostgreSQL |
| `worker` | Читает новые заказы из PostgreSQL и помечает обработанными |

Основные эндпоинты API:

| Эндпоинт | Назначение |
|---|---|
| `GET /health` | Возвращает `ok`; при `HEALTH_FAIL=true` — ошибку 503 |
| `POST /order` | Создает заказ в PostgreSQL |
| `GET /orders` | Возвращает последние 100 заказов |
| `GET /metrics` | Отдает метрики Prometheus |
| `GET /fail` | Намеренно возвращает 500 для проверки алерта |
| `GET /slow`, `GET /load` | Сохранены для проверок задержки и нагрузки |

У worker тоже есть HTTP-сервер с `/health` и `/metrics`. Его health-проверка учитывает работу фонового цикла, но не требует постоянной доступности БД: сбой PostgreSQL не должен перезапускать все приложения по liveness.

Для каждого сервиса подготовлены `server.py`, `observability.py`, `db.py`, `requirements.txt`, `Dockerfile` и `.dockerignore`. Сохранены JSON-логи, метрики и инструментация OpenTelemetry. Пароли в исходники не записывала.

Две реплики worker выбирают заказы через `FOR UPDATE SKIP LOCKED`: занятая одной репликой строка пропускается другой. Выбор заказа и отметка `processed` выполняются в одной транзакции. В этой лабе обработка — только изменение записи в БД, без внешних платежей и других побочных действий.

Сначала подготовила сервисы, но устанавливать их стала только после настройки политик.

## Часть 1 — Ограждения на кластер

### Установка Kyverno

Выбрала Kyverno: политики описываются Kubernetes-манифестами с CEL-выражениями, для этой лабы такой вариант понятнее, чем отдельно осваивать Rego в Gatekeeper.

При создании ресурса API-сервер обращается к admission webhook. Если политика запрещает Pod, его создание отклоняется до сохранения — kubelet такой Pod запускать не начинает.

Установила Kyverno через Helm:

```bash
helm repo add kyverno https://kyverno.github.io/kyverno/
helm repo update

helm upgrade --install kyverno kyverno/kyverno   --version 3.9.2   --namespace kyverno --create-namespace   --kube-context lab2   --wait --timeout 10m
```

Версия Kyverno — `1.19.2`, Kubernetes — `1.37.0`. Эта версия Kubernetes была новее диапазона, указанного в проверенной таблице совместимости Kyverno, поэтому установку и работу правил проверяла на своем стенде. Успешные проверки не означают гарантированную совместимость всех возможностей.

Все четыре контроллера запустились, webhook-конфигурации зарегистрировались:

<img src="images/img1.png" alt="img1" width="700">

*img1 — Контроллеры Kyverno и зарегистрированные webhook-конфигурации*

При установке появилось предупреждение об устаревании `ClusterPolicy`. Поэтому использовала новый тип `policies.kyverno.io/v1`, `ValidatingPolicy`.

Настроила пять кластерных политик:

| Файл | Правило | Польза |
|---|---|---|
| `disallow-privileged.yaml` | Запрет `privileged: true` у обычных и init-контейнеров | Контейнер не получает чрезмерные привилегии |
| `require-limits.yaml` | Обязательные лимиты CPU и памяти | Ограничение потребления ресурсов отдельным контейнером |
| `require-labels.yaml` | Непустые метки `app` и `owner` | Понятно, к чему относится Pod и кто за него отвечает |
| `disallow-host-namespaces.yaml` | Запрет `hostNetwork`, `hostPID`, `hostIPC` | Сохранение изоляции от сети, процессов и IPC ноды |
| `allowed-images.yaml` | Разрешены только выбранные репозитории образов | Произвольный образ не пройдет admission |

У всех политик задано `validationActions: [Deny]`. Проверяются операции создания и обновления Pod.

Из области действия явно исключены `kube-system`, `kube-public`, `kube-node-lease`, `kyverno`, `monitoring`, позднее добавлен `cnpg-system`. Это инфраструктурные исключения: например, агентам мониторинга может понадобиться доступ к ноде. Namespace `lab3`, в том числе Pod PostgreSQL, остается под проверками. Поэтому «кластерная политика» здесь не означает отсутствие исключений.

### Общая проверка пяти нарушений

Подготовила пять сырых манифестов в `tests/`. Проверяла их через API-сервер без фактического запуска опасных контейнеров:

```bash
  minikube -p lab2 kubectl -- apply --dry-run=server -f "$file"
```

Сначала тесты получились не совсем независимыми: Pod без лимитов одновременно не имел меток, а privileged-тест тоже нарушал несколько правил. При исправлении еще сбились отступы YAML — получила `mapping values are not allowed in this context`.

Исправила отступы и привела каждый файл к одному нарушению. В итоге:

| Тест | Единственный отказ |
|---|---|
| `foreign-image-pod.yaml` | `allowed-images` |

### Rolling update

Для управляемого обновления задала:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
minReadySeconds: 5
progressDeadlineSeconds: 120
```

При четырех желаемых репликах можно создать один дополнительный Pod. Исправные старые Pod не удаляются, пока не появится достаточно доступных новых. Завершающиеся Pod некоторое время еще могут отображаться в списке.

Подготовила отдельный образ `shop-api:v2`, затем поменяла тег API в `values.yaml` и запустила обновление.

Одновременно из существующего worker непрерывно отправляла запросы к `http://shop-api:8080/health` через Service. Каждый запрос открывал новое соединение. Для этого теста не использовала port-forward как путь нагрузки: он выбирает один Pod, и его удаление могло бы оборвать проверку независимо от состояния Service.

Обновление завершилось сообщением `successfully rolled out`: четыре готовых Pod перешли на `v2`. Данные о версии также выводятся приложением; колонка `APP VERSION` в истории Helm — отдельное поле из `Chart.yaml`, а не доказательство тега запущенного образа.

### Сломанное обновление и rollback

Теперь специально сломала новую конфигурацию: установила `api.healthFail: true` и снова сделала `helm upgrade`.

Новый Pod запускался, но возвращал 503 на `/health`: readiness не проходила, трафик в него не направлялся. Liveness также перезапускала контейнер. Четыре старых исправных Pod остались работать.

Обновление завершилось ошибкой `Progress deadline exceeded` по нашему `progressDeadlineSeconds`, раньше общего таймаута Helm. Это ожидаемая часть эксперимента, автоматического отката не произошло:

<img src="images/img23.png" alt="img23" width="700">

*img23 — Неудачная ревизия 4: четыре исправных Pod и один неготовый*

Откатилась на последнюю успешную ревизию 3:

```bash
helm rollback shop 3   --namespace lab3   --kube-context lab2   --wait --timeout 3m
```

Rollback создал новую ревизию 5 с прежней рабочей конфигурацией, история сохранилась:

<img src="images/img24.png" alt="img24" width="700">

*img24 — Успешный rollback на конфигурацию ревизии 3*

После отката отдельно вернула `api.healthFail: false` в локальный `values.yaml`. Helm rollback меняет релиз в кластере, но файл на диске не исправляет — иначе следующий upgrade снова внес бы поломку.

За время непрерывного наблюдения, включая обновление, сломанную версию и откат, получилось **1444 запроса, `failed=0`**. Это результат нашего тестового потока, а не гарантия отсутствия ошибок при любой нагрузке.

Для API цепочка управления — Deployment → ReplicaSet → Pod. Контроллер ReplicaSet входит в стандартный kube-controller-manager и поддерживает количество Pod.

PostgreSQL управляет отдельный контроллер CloudNativePG: он понимает собственный CRD `Cluster`, роли primary, инициализацию БД, сертификаты и хранилище. Механизм reconciliation общий, но предметная логика разная. Именно CloudNativePG восстановил Pod нашей базы.

### Три алерта в чарте

В `templates/prometheusrules.yaml` добавила объект `PrometheusRule` с меткой `release: monitoring`.

| Алерт | Условие | Почему важно и что делать |
|---|---|---|
| `ShopAPIDown` | Все существующие цели API имеют up=0 либо цели отсутствуют; `for: 1m` | Проверить Pod, readiness, Service и пользовательскую доступность API |
| `ShopHighErrorRate` | Общая доля 5xx выше 20% в минутном окне; `for: 1m` | Пользователи получают ошибки; проверить логи, PostgreSQL и последние изменения |
| `ShopWorkerStalled` | Нет свежего успешного опроса БД среди доступных worker более 60 секунд либо подходящие метрики отсутствуют; `for: 1m` | Обработка заказов может остановиться; проверить worker и базу |

Все три имеют `severity: critical`. `ShopAPIDown` по метрике up проверяет доступность сбора метрик, а не полноценный пользовательский HTTP-сценарий.

Для доли ошибок сначала суммируются скорости ошибок и всех запросов по репликам, затем выполняется деление. Складывать проценты реплик нельзя: они могут получать разное количество запросов.

Для worker используется максимальная временная метка последнего успешного опроса среди Pod с `up=1`. Даже если один worker давно не работал, второй может продолжать обрабатывать очередь. Проверка успешного опроса не доказывает выполнение каждого заказа, но обнаруживает отсутствие успешного доступа worker к БД.

Правила загрузились в Prometheus, у всех `health=ok`, ошибок вычисления нет:

### Дашборд Grafana

В существующей Grafana собрала дашборд shop с тремя панелями.

**1. Доступные цели по сервисам:**

```promql
sum by (service) (
  up{namespace="lab3", service=~"shop-api|shop-worker"}
)
```

В норме API — 4, worker — 2. Здесь нужна сумма значений up, а не число рядов: при одной неработающей цели из четырех `sum(up)=3`, но `count(up)=4`.

**2. Доля ошибок API, %:**

```promql
100 * (
  sum(rate(api_requests_total{
    namespace="lab3", service="shop-api", status=~"5.."
  }[1m])) or vector(0)
)
/
clamp_min(
  sum(rate(api_requests_total{
    namespace="lab3", service="shop-api"
  }[1m])),
  0.000001
)
```

На панели показан порог 20%. Линия порога — оформление графика, само правило алерта находится в PrometheusRule.

**3. Время с последнего успешного опроса БД worker:**

```promql
time() - max(
  shop_worker_last_success_timestamp_seconds{
    namespace="lab3", service="shop-worker"
  }
  and on(namespace, pod)
  (
    up{namespace="lab3", service="shop-worker"} == 1
  )
)
```

При пустой очереди значение тоже обновляется: worker успешно опрашивает БД, даже если заказов нет. Если метрик нет вообще, панель может показать No data; алерт отдельно учитывает это через `absent`.

И конечно, без времени на виртуалке снова не обошлось... На Mac было около 19:30, а VM жила примерно в 19:18. Графики заканчивались раньше правого края, а после перевода часов появлялись разрывы. Рост старого участка панели worker сам по себе не стал доказательством сбоя БД: текущий запрос в Prometheus показывал последние успехи около 4 и 16 секунд назад.

Сначала еще и запустила команду синхронизации из Ubuntu, подключившись по SSH к ней же. Время виртуалки успешно скопировалось на ту же виртуалку — полезность примерно нулевая :)

В итоге выполнила команду именно в терминале Mac, чтобы взять его текущее время:

```bash
ssh -t patineshka@192.168.64.2   "sudo timedatectl set-ntp false && sudo date -u -s '@$(date -u +%s)' && sudo hwclock --systohc --utc && sudo timedatectl set-ntp true"
```

- Пять кластерных политик с явными инфраструктурными исключениями; нарушающие Pod отклоняются
- Helm-чарт shop с API, worker, объектом PostgreSQL, ServiceMonitor и PrometheusRule

- Обновление API и rollback сломанной конфигурации; в тестовом потоке 1444 запроса без ошибок
- Заказ сохраняется в PostgreSQL, обрабатывается worker и переживает пересоздание Pod БД
- При отключенном API-сервере управление ресурсами недоступно, но работающие сервисы продолжают отвечать
- Метрики шести целей в Prometheus, три правила алертов, firing в Karma и доставка webhook
- Дашборд и экспорт его конфигурации

Текущие значения для стенда: API — 4 реплики после теста масштабирования (начинала с 3), worker — 2, PostgreSQL — 1. `HEALTH_FAIL` возвращен в `false`, API-сервер восстановлен, нагрузочные проверки остановлены.

## Топ ошибок

К сожалению, без приключений снова не обошлось. Вот мой топ затыков (затупов):

1. **Тестировала одно правило, нарушала сразу три.** В privileged-тесте забывала лимиты и метки, а потом получала несколько отказов. Для понятной проверки каждому манифесту оставила ровно одно нарушение.

2. **YAML и отступы — отдельный вид отношений.** При добавлении labels получила `mapping values are not allowed in this context`. Исправила отступы, и только после этого запрос вообще дошел до политик.

3. **Путала readiness и liveness.** Обе ходили на один `/health`, поэтому казалось, что делают одно и то же. Но одна убирает Pod из обслуживания трафика, а другая перезапускает контейнер. Особенно хорошо это стало видно на сломанном обновлении.

4. **Метки есть, но не там.** Метки Deployment, метки его Pod и inheritedMetadata у Cluster — разные места. Наличие owner у управляющего объекта еще не означает, что owner появился у Pod.

5. **Попыталась восстановить то, что еще не отключила.** Первой выполнила обратную команду перемещения манифеста API-сервера и получила `cannot stat`. Хорошо, что файл просто не существовал, а ничего другого не произошло.

6. **Думала, worker ничего не обработал, потому что в tail нет записи.** Запись была, но ее уже вытеснили health-пробы. Отфильтровала полный доступный лог и нашла `Order processed`.

7. **Время на VM снова решило жить своей жизнью.** К третьей лабе это уже почти традиция. Отдельное достижение — синхронизировать VM с ней же, запустив команду не в том терминале. Теперь перед разбором пустых графиков сначала сравниваю часы Mac и Ubuntu.

8. **Failed to fetch выглядел страшнее причины.** Grafana работала, а проблема оказалась на пути через проброс VSCode. И да, второй port-forward не может занять уже занятый моим же первым процессом порт.

Самое полезное в этой лабе — специально что-нибудь сломать, а потом увидеть, кто именно это чинит. ReplicaSet восстановил API, оператор — PostgreSQL, а готовность новой версии и сохранение трафика пришлось обеспечить настройками обновления. Само слово Running оказалось далеко не всей историей ;)
